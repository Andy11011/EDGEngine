1) For trades — Event Sourcing is the right choice

Yes, absolutely. Trade execution involves a strict lifecycle 
(Submitted → Accepted → PartiallyFilled → Filled → Cancelled → Rejected).

Why event sourcing: You need a complete, immutable audit trail for compliance and debugging. You can reconstruct the exact state of any order at any point in time.
Crucial benefit: You can replay events to regenerate P&L, fee calculations, or slippage analysis if your accounting logic changes later.
Do not just store the latest state—you'll lose the "why" and the exact sequence.


2) Account state — Event Sourcing is also better, but with a nuance

Yes, but treat it as a derived projection. Your account balance, equity, margin, and available funds are calculations based on trade events, deposit/withdrawal events, and fee events.

Storing only the current balance is dangerous—if a trade replay fixes a fill price, your balance would be wrong forever.

Best practice: Store account events (e.g., AccountDeposited, MarginLocked, TradeSettled), and build a read-model projection (e.g., a PostgreSQL table with the current account snapshot).

This way, you get the audit trail and fast reads for the UI.

3) Configuration — Simple record (CRUD) is perfectly fine

Yes, stick with a simple key-value store or a SQL table.

Configuration (Telegram chat ID, risk limits, API keys, trading pairs) changes rarely and doesn't need historical replay.

Overcomplicating this with event sourcing gives you zero benefit—just extra storage and complexity. Use a basic config table with key/value columns.

4) Which DB for event storage? Postgres, NOT Redis

Postgres is excellent for event sourcing. Redis is completely unsuitable as the primary source of truth for financial events.

Why Postgres:

ACID transactions (critical — you must never lose an event or write it partially).

Use a single events table with columns: id (UUID), aggregate_id (order_id or account_id), version, event_type, payload (JSONB), created_at.

JSONB allows flexible schemas and fast querying on event data.

Postgres can handle millions of events easily on a t3.micro if you index properly ((aggregate_id, version)).

Why NOT Redis:

Redis is in-memory and primarily for caching. It has optional persistence (RDB/AOF), but it is not crash-safe in the same transactional way. If Redis restarts before flushing, you lose financial data — unacceptable.

You can use Redis as a cache for the current projected state (e.g., current account balance) to speed up reads, but the source of truth must be Postgres.

5) Can it fit into AWS t3.micro (1 vCPU, 1GB RAM)?

Yes, it is absolutely possible, but you need to be disciplined:

Memory budget: 1GB is tight. Postgres itself needs ~200–300MB. Your Python/Go/Rust app needs ~100–200MB. The OS and Docker overhead take another ~200MB. You'll have ~300–400MB left for caches and connections.

Optimizations:

Use async workers (FastAPI with Uvicorn, or Node.js) to handle concurrency without spawning heavy threads.

Set max_connections=20 in Postgres (default is 100, which will OOM your t3.micro).

Do not load all events into memory to rebuild state. Use snapshots: store a current_state snapshot every 100 events (e.g., in a account_snapshots table) so you only replay the last 100 events on startup, not the entire history.

Use Redis only for session caching or pub/sub — keep its maxmemory small (~128MB).

Swap: Enable swap space (e.g., 2GB) on the EBS volume to avoid OOM killer, but performance will degrade — so keep it as a safety net, not a crutch.

Verdict: t3.micro works for a small-to-medium trader (a few hundred trades per day). If you hit thousands per second, you'll need to scale up.

6) Microservices, shared Redis, and whether it defeats the purpose

Let's clear up the dogma: "Each microservice must have its own database" refers to the write database (source of truth).

Now, the bigger question: Do you even need microservices for this?

Honest advice: For a single developer or small team running on t3.micro, a modular monolith is vastly simpler and cheaper.

Keep edge-trader (trading engine) and edgeDesk (UI backend) as two separate deployable containers for independent scaling, but let them share one Postgres database (with different schemas: trading.events, ui.config).

If you insist on microservice purity, give each its own separate Postgres database (still on the same t3.micro instance using different ports/names — e.g., db_trader, db_ui). That satisfies the principle without extra cost.

First, what this design is called:
In industry terms, this is a hybrid of:

1. CQRS (Command Query Responsibility Segregation) – because Commands (writes) go through an API, while Queries (reads) go straight to the database.

2. Shared Kernel (from Domain-Driven Design) – because both services share a common database model, but with strictly defined Bounded Contexts (who owns which tables).

3. More casually, it's called the "Single-Writer / Multi-Reader" pattern.

Here is the golden rule for Event Sourcing when multiple services write to the same database:

Event Tables are Append-Only Logs (Multi-Writer allowed).
Snapshot Tables are Mutable State (Strictly Single-Writer).

If both EdgeDesk (Java) and edge-trader (Rust/Python) try to update the account_snapshots balance at the exact same millisecond (e.g., Java deducts for a withdrawal, Rust adds P&L for a fill), 
you will get lost updates, race conditions, and a corrupted account balance. On a single t3.micro with 1 CPU, you cannot run a distributed locking mechanism (like ZooKeeper) to coordinate this.

Step A: The Event Table (Append-Only Log)

CREATE TABLE order_events (
    id BIGSERIAL PRIMARY KEY,           -- Global sequential ID (for easy polling)
    aggregate_id UUID NOT NULL,          -- The order's unique ID
    version INT NOT NULL,                -- Monotonic version per aggregate (1,2,3...)
    event_type VARCHAR(50) NOT NULL,     -- 'OrderPlaced', 'OrderFilled', 'OrderCancelled'
    payload JSONB NOT NULL,              -- Flexible payload: {"price": 60000, "qty": 0.5}
    created_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- The magic bullet that prevents race conditions:
    CONSTRAINT unique_aggregate_version UNIQUE (aggregate_id, version)
);

-- Index for fast recovery of a specific aggregate:
CREATE INDEX idx_order_aggregate ON order_events(aggregate_id, version);

You are completely justified in disliking the "constant polling" (the SELECT WHERE id > $1 every 250ms). It feels primitive, adds unnecessary database load, and just feels wrong in a modern architecture.


Option 1: The "REST API" Trigger (Your Suggestion)
EdgeDesk calls edge-trader API to say "Hey, I wrote an event!"

How it works: Java appends the event to Postgres, then immediately makes an HTTP POST /edge-trader/internal/notify to wake Rust up.

The fatal flaw: Rust must process this request synchronously before replying to Java. If Rust is busy reconciling a trade or its connection to the exchange lags, the Java UI hangs. Worse, if Rust crashes after Java sends the notification but before Rust processes it, the event is lost forever (because Java already returned 200 OK to the user).

Verdict: Avoid. It re-introduces synchronous coupling and failure modes that Event Sourcing is designed to eliminate.


Option 2: The Message Broker (Kafka, RabbitMQ, Redis Streams)
The "Pure Microservice" way.

How it works: Java writes the event to Postgres and publishes a message to Redis Streams/SQS. Rust subscribes to the stream and processes instantly.

The t3.micro reality:

Redis Streams uses ~50-80MB RAM (bearable).

RabbitMQ uses ~200MB+ (too heavy).

AWS SQS (external) costs a few cents and uses 0 RAM—but adds 20-50ms network latency per message.

The hidden cost: Now you have to manage exactly-once delivery. If Rust processes the message but crashes before updating the snapshot, you get duplicate processing. You now need idempotency logic (checking if an event already exists) which you already get for free with Postgres UNIQUE constraints.

Verdict: Overkill. It adds a second infrastructure piece to monitor, backup, and secure for a marginal gain over polling.

Option 3: Postgres LISTEN / NOTIFY (The Absolute Sweet Spot)
Push-based notification built directly into Postgres. No extra services. No polling.

This is the hidden gem of Postgres that solves your exact problem.

How it works:

1. EdgeDesk (Java): After inserting the event, immediately run:

sql
NOTIFY new_events, 'order_placed';
(You can put this in a AFTER INSERT trigger so Java doesn't even have to remember to call it!)

2. Edge-trader (Rust): Maintains one dedicated Postgres connection that is always listening:

// In Rust (using sqlx or tokio-postgres)
let mut listener = postgres.connect().await?;
listener.execute("LISTEN new_events").await?;

while let Some(notification) = listener.recv().await {
    // Wakes up IMMEDIATELY (millisecond latency) when Java writes an event.
    // Now go poll for new events since last_processed_id.
    process_new_events().await?;
}

3. The Fallback (Safety net): Even with LISTEN, keep a lightweight poller that runs every 30 seconds 
just to catch any notifications that might have been missed if Rust crashed and reconnected. This 
gives you 100% reliability.
