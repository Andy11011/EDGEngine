Why node.run_async() is not truly asynchronous
The TradingNode in Nautilus is designed as the main entry point of a trading application. 
Its run_async() method typically does something like:

python
async def run_async(self):
    # ... setup ...
    await self.kernel.run()   # or loop.run_forever()
However, the underlying Kernel.run() (or the internal event loop handling) often uses
 loop.run_forever() or a blocking while‑loop that does not yield. Even if it's wrapped
  in an async function, if it calls loop.run_forever(), that call takes over the thread
   and never returns until the loop stops – it doesn't give other coroutines a chance to run,
    because it is running the event loop itself, not awaiting something that yields.

In other words, when you await node.run_async(), you are effectively handing over the entire 
event loop to the node’s internal runner. That runner consumes all available CPU time for its 
own scheduling, starving your server.serve() and listen_trade_events coroutines.

//********************************//

boto3 is a synchronous library. Wrapping the call in async def receive_trade_events(...) does not make 
sqs_client.receive_message() non-blocking — it's still a plain blocking network call under the hood. 
With WaitTimeSeconds=20, this single line blocks the entire event loop for up to 20 seconds, every 
single poll cycle, forever. Same for delete_message(). During those 20-second windows, uvicorn literally
 cannot process any incoming HTTP connection — the loop is busy sitting inside boto3's socket read.


With run_async() commented out: the node never starts, so is_running never becomes True. listen_trade_events() 
gets stuck forever in that harmless sleep(0.5) loop and never reaches receive_trade_events() → never calls 
sqs_client.receive_message(..., WaitTimeSeconds=20). The blocking boto3 call simply never executes. That's why
the API "works" — not because run_async() was the thing freezing the loop, but because removing it prevents
the real blocking call (the sync boto3 SQS poll) from ever being reached.

//********************************//

So the blocking call still happens synchronously — it hasn't magically become non-blocking — but it's now
 happening on a separate OS thread, so it no longer occupies the single thread that the event loop itself 
 runs on. That's the entire trick: you can't make boto3 async, but you can move it off the thread that matters.

This job step configures AWS credentials for the integration_tests job using OIDC (OpenID Connect)
 federation instead of long-lived AWS access keys. Here's the breakdown:

What each part does:

needs: build_amd64 — this job won't run until the build_amd64 job finishes successfully.
runs-on: ubuntu-latest — runs on GitHub's standard Ubuntu runner.
actions/checkout@v4 — pulls your repo's code onto the runner so the integration tests have access to it.
aws-actions/configure-aws-credentials@v4 — this is the key step. It uses GitHub's OIDC token to assume an IAM role in AWS without needing static AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY secrets. GitHub presents a signed OIDC token to AWS STS, and if your IAM role trusts that token, AWS hands back temporary credentials scoped to that role.
aws-region: ap-southeast-1 — the AWS region the credentials/session will target (matches wherever your CodeBuild project lives).
